# Integration-тесты

Общий подход к integration-тестам в этом репозитории — бьём в настоящую инфраструктуру (Postgres пока что, но принцип не завязан на конкретную БД), не мокаем то, что тестируем. Через `@fms/fixtures` — читай сначала [`../db/fixtures.md`](../db/fixtures.md) про жизненный цикл тестовой БД, тут — как это использовать в самом тесте.

## Философия: почему без моков

Репозитории (`Kysely*Repository` и аналоги) — тонкий слой над SQL. Замокать `Kysely`/`pg` в тесте репозитория означает протестировать не репозиторий, а собственный мок — легко получить зелёные тесты, которые ничего не проверяют. Ошибки вроде неверного маппинга колонки, забытого `WHERE`, не той enum-строки в БД — все они живут на границе с реальной СУБД и видны только если тест реально туда ходит.

Плата — тесты становятся integration, не unit: медленнее, нужен запущенный Postgres, состояние между тестами нужно чистить руками. Осознанный компромисс для кода, единственная работа которого — говорить с базой.

## Общий скелет теста

Один `db`-инстанс на файл (не на тест), сброс состояния в `beforeEach`, закрытие соединения в конце:

```ts
const db = createKyselyInstance(testDatabaseConfig());
const repo = new SomeRepository(db);

beforeEach(() => truncateAllTables(db));
afterAll(() => db.destroy());
```

`testDatabaseConfig()`/`truncateAllTables()` — из `@fms/fixtures`. Пересоздание самой БД (`resetTestDatabase()`) происходит один раз на весь прогон через Jest `globalSetup`, не на каждый файл/тест — это дорогая операция, `truncateAllTables` между тестами достаточно для изоляции.

## Фикстуры-строки — локально, не в общем пакете

Когда тесту нужна связанная строка для FK (родительская сущность, которой нет отдельного репозитория/порта в `@fms/core`), она заводится прямо в тестовом файле через тот же `db`, простой хелпер вида `async function seedX() { ... }`. `@fms/fixtures` отвечает за жизненный цикл БД целиком (создать/сбросить/почистить) — не за фабрики конкретных строк для конкретных тестов, это осталось намеренно локальным.

## Что обычно стоит проверять у репозитория

Не жёсткий чеклист, но типичный набор кейсов, применимый к любой новой сущности:

- **find/get** — не найдено → `null`/`[]`, найдено → ожидаемая строка.
- **create** — успех с сгенерированным id; нарушение уникальности → `DuplicateEntryError`; если есть FK на другую сущность — несуществующий id родителя → `NotFoundError`.
- **update** — успех меняет поля; отсутствующий id → `NotFoundError`.
- **archive/delete** (что из них есть у конкретной сущности) — успех; отсутствующий id → `NotFoundError`.
- **Опциональные/nullable поля** — если в домене поле необязательное (`undefined`), а в колонке — nullable (`null`), проверить round-trip именно как `undefined`, не как утёкший `null`.
- **Численные поля** (`DECIMAL`/`NUMERIC` в схеме) — проверить, что значение приходит как `number`, не `string` (see [`../db/kysely.md`](../db/kysely.md) про фикс type-parser'а).
- **Комбинируемые фильтры** (`find(filter)`-стиль методы) — каждое поле фильтра по отдельности и в комбинации (AND), не только "хотя бы один сценарий работает".

## Технические грабли

### `kysely` — чистый ESM, Jest по умолчанию его не видит

Любой ESM-only пакет в `node_modules` (`"type": "module"` в его `package.json`) не транспилируется Jest'ом по умолчанию — падает с `SyntaxError: Unexpected token 'export'` при попытке `require()`. Фикс — явно пустить такой пакет через transform:

```js
transformIgnorePatterns: ["node_modules/\\.pnpm/(?!(<имя-пакета>@))"]
```

Важно: `pnpm` кладёт реальные пакеты не плоско (`node_modules/<pkg>/...`), а под `node_modules/.pnpm/<pkg>@<версия>/node_modules/<pkg>/...`. Наивный паттерн `"node_modules/(?!<pkg>)"` матчится на первом `node_modules/` (перед `.pnpm`) и игнорирует файл ещё до того, как дойдёт до имени пакета. Паттерн должен целиться именно в `.pnpm/<имя>@` сегмент.

### `maxWorkers: 1`, если тесты шарят состояние

Jest по умолчанию гоняет файлы тестов в параллельных воркерах. Если несколько файлов работают с одной и той же внешней БД и чистят её между тестами (`beforeEach`/`truncate`), параллельный запуск — гонка: один файл может очистить данные, с которыми ещё работает другой. `maxWorkers: 1` в корневом `jest.config.cjs` убирает этот класс проблем целиком, ценой более медленного прогона. Гонка не обязательно воспроизводится стабильно — отсутствие наблюдаемого флейка в нескольких прогонах не значит, что её нет.

### Реальная БД ловит то, что `tsc` не может

Пример из практики: enum в домене со строковыми значениями (`RUB = "RUB"`) и такой же enum с числовыми значениями по умолчанию (`RUB = 0`) неотличимы на уровне TypeScript-типов — оба `Currency`, оба присваиваются друг другу. Разница проявляется только в рантайме, когда числовое значение улетает в Postgres ENUM-колонку и база отвечает `invalid input value for enum`. `pnpm -r check:types` такую ошибку не поймает в принципе — только реальный insert через реальный драйвер.

## Как добавить новый файл

1. Тот же скелет: `db` + репозиторий/клиент под тест, `beforeEach` truncate, `afterAll` destroy.
2. Локальные `seedX()`-хелперы под FK-зависимости, если нужны.
3. Файл кладётся в `__jest__/integration/` соответствующего пакета, `testMatch` в `jest.config.cjs` подхватывает его автоматически — сам конфиг трогать не нужно, пока пакет уже зарегистрирован в `projects`.
